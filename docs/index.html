Part 1

What are Git and GitHub?

  • [1:00] Target: finish Part 1 by ~6:00.
  • Quick poll by hands: who has used Git before? Who has emailed a file called final_v2_REAL.docx?

Sound familiar?

report.docx
report_v2.docx
report_v2_final.docx
report_v2_final_FIXED.docx
report_v2_final_FIXED_use_this_one.docx

Which one is real? What changed? Who changed it?

  • [~1 min] Everyone has done this. It breaks down with two or more people, and with code it breaks fast.
  • Version control answers: what changed, when, who, and why, and lets you go back.

Git

  • A program on your computer
  • Takes snapshots of a project folder
  • Each snapshot = a commit: what changed, who, when, why
  • Works offline, free, open source
  • [~1 min] Define: repository (repo) = a project folder that Git is tracking, including its full history.
  • Commit = a saved snapshot plus a short message. Think "save point in a video game".
  • Git was written in 2005 by Linus Torvalds to manage the Linux kernel. It is now the industry standard.

GitHub

  • A website that hosts Git repos
  • Share, back up, and collaborate
  • Adds teamwork tools: pull requests, issues, reviews, automated checks
  • [~1 min] GitHub is one host; GitLab and Bitbucket are others. Git works the same with all of them.
  • Your GitHub profile also doubles as a portfolio employers look at.

Git vs GitHub

Git

  • Tool you install
  • Runs on your laptop
  • Tracks history
  • Like: a camera

GitHub

  • Website you sign in to
  • Runs in the cloud
  • Shares history with others
  • Like: a shared photo album
  • [~1 min] The most common beginner confusion. You can use Git without GitHub; GitHub is useless without Git.
  • VS Code is a third thing: an editor that gives Git a friendly button interface.

Why engineers use version control

  • Undo anything, any time
  • Work in parallel without overwriting each other
  • Traceability · why did this change? who approved it?
  • Backup · laptop dies, project lives
  • Expected in every internship and job
  • [~1.5 min] Engineering angle: design reviews, traceability for safety-critical work, reproducing exactly what was tested.
  • Not only code: firmware, scripts, LaTeX reports, config files, documentation.
  • Senior design teams that skip this lose work every semester.

Tell Git who you are

Once per computer. Every commit gets stamped with this.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Use the email on your GitHub account, or GitHub's private noreply address (Settings → Emails).

  • [~1 min] This is the one thing we must do in a terminal. In VS Code: Terminal → New Terminal.
  • If the email doesn't match your GitHub account, your commits won't link to your profile (they still work).
  • Check with git config --global --list.

Part 3

How Git thinks

Local vs remote

  • [9:00] The most important mental model of the day. If they get this slide, everything else is buttons.

Four places your work lives

  • [~3 min] Walk left to right. Working folder: normal files. Staging: you choose which changes go in the next snapshot. Local repo: snapshots saved on your laptop only. Remote: the copy on GitHub everyone shares.
  • Key point: commit is local. Nobody sees it until you push. Pull brings others' commits down.
  • Analogy: staging = items in your shopping cart, commit = checkout, push = shipping it to everyone.

Getting a repo

Start fresh

Turn a folder into a repo

VS Code: Source Control → Initialize Repository

git init

Copy an existing one

Download a repo + all its history

VS Code: Clone Git Repository…

git clone <url>
  • [~1 min] init: for your own new projects. clone: for joining an existing project, which is what we do today.
  • A clone automatically remembers where it came from; that remote is called origin.

The everyday loop

  1. Pull · get the latestgit pull
  2. Edit files
  3. Stage · click + next to the filegit add <file>
  4. Commit · type a message, click Commitgit commit -m "Message"
  5. Push · Sync Changes / Publish Branchgit push
  • [~1.5 min] This is 90% of Git. Small grey text = the terminal equivalent; you never have to type it today but it's good to recognize.
  • git status answers "what's going on?" at any moment; VS Code's Source Control panel is a live git status.

Part 4

Branches & pull requests

  • [15:00] Three slides of concept, then Lab 1. Keep it under 3 minutes.

A branch is a parallel line of work

  • main = the official version
  • Make a branch, experiment safely, main stays clean
  • One branch per task

VS Code: click the branch name (bottom-left) → Create new branch…

git switch -c name/your-username · switch back: git switch main
  • [~1 min] Branches are cheap: just a label pointing at a commit. Make them freely.
  • Switching branches changes the files in your folder to match that branch. Commit (or discard) before switching.
  • In this repo, main is protected: nobody, including you, can push to it directly. Everything goes through a pull request.

Pull request (PR)

"Here's my branch. Please review it and merge it into main."

  • Shows exactly what changed
  • Teammates comment and approve
  • Automatic checks run (ours: Workshop check)
  • [~1 min] Merge = combine the commits of one branch into another.
  • Our robot "Workshop check" runs on every PR. In Lab 1 it just checks you only edited ATTENDEES.md. Green check = good, red X = click Details and read the message.
  • The instructor merges PRs today.

Part 5

Merge conflicts

Not an error. A question.

  • [30:00] By now several PRs are merged, so most remaining PRs say "This branch has conflicts that must be resolved". That's the lab.

Why your PR conflicts

  • Everyone added a line in the same spot
  • main moved on since you branched
  • Git can't guess which line goes first, so it asks you
<<<<<<< HEAD (yours, "current")
- Sam Lee (@samlee) — Mechanical Engineering
=======
- Ana Ruiz (@anaruiz) — Computer Science
>>>>>>> origin/main (theirs, "incoming")
  • [~2 min] Conflicts happen only when two branches change the same lines. Different files or far-apart lines merge automatically.
  • The markers are just text Git writes into the file. Resolving = editing the file so it's what you want, deleting the marker lines, and committing.
  • Here the right answer is obvious: keep both names.
Hands-on · Lab 2 · 8 min

Resolve your conflict

  1. On your name/… branch: … → Fetch
  2. … → Branch → Merge… → pick origin/maingit pull origin main
  3. Open ATTENDEES.md → Accept Both Changes
  4. Keep every name. Delete nothing. No <<< left.
  5. Save → stage + → Commit → Sync Changes
  6. Your PR updates itself; check goes green

Stuck? GitHub's Resolve conflicts button on the PR works too. Full steps in LABS.md

  • [32:00–40:00] Demo once with your own test branch. VS Code shows the conflict inline with clickable "Accept Current | Accept Incoming | Accept Both". The Merge Editor button gives a 3-pane view; "Accept Combination" is the same idea.
  • The merge commit message is pre-filled; just click Commit.
  • Keep merging PRs as they go green; some people will conflict twice. That's realistic, repeat the steps.
  • No conflict? Your PR was merged early, or nobody's merged yet. Help a neighbor.
Part 6 · demo

History & undo

  • [40:00] Instructor demo, 5 minutes. Attendees watch; hands off keyboards.
  • Do the revert on a demo branch (e.g. demo/revert), never directly on main.

Viewing history

  • VS Code: Source Control Graph · every commit, every branch
  • VS Code: Timeline (Explorer, bottom) · one file's history
  • GitHub: the commits link (clock icon)
git log --oneline --graph
  • [~2 min] Show the graph after Lab 1/2: lots of name branches merging into main. Point out a merge commit with two parents.
  • Each commit has an ID (SHA), like 3f2a9c1. The first 7 characters are enough.
  • Click a commit to see its diff. Good commit messages make this readable; bad ones ("stuff") make it useless.

Undo, safely

SituationVS CodeTerminal
Throw away unsaved edits to a fileDiscard Changes ↶git restore <file>
Unstage a fileUnstage −git restore --staged <file>
Undo a commit that's already pushed(terminal)git revert <sha>

revert adds a new commit that undoes an old one. History stays honest. git reset also exists: it rewrites history, so be careful and never on shared branches.

  • [~3 min] Demo: make a bad commit on demo/revert, push, git log --oneline, copy the SHA, git revert <sha>, save the default message, push. Show both commits in the graph.
  • Discard Changes is permanent for uncommitted work. Committed work is almost never lost.
  • Reset: mention only. It's how people lose work and break teammates' clones.
Part 7

Working as a team

Issues · reviews · checks

  • [45:00] Two concept slides then Lab 3. The repo has 50 bug issues, more than there are people.

Issues: the team's to-do list

  • One issue = one task or bug
  • Labels to filter · Assignee = who's on it
  • A PR that says Closes #12 closes issue 12 when merged
  • [~1 min] Show the Issues tab: filter by label workshop-bug and a language label.
  • Assigning yourself prevents two people fixing the same thing. Only pick unassigned issues.
  • Senior design: put every task in issues; it doubles as your progress log for advisors.

Code review

  • PR → Files changed → read the diff
  • Click a line to comment
  • Review changes → Comment / Approve / Request changes
  • Be kind and specific

Collaborator

Write access to the same repo. Teams, today.

Fork

Your own copy; PR back to the original. Open source.

  • [~1.5 min] Reviewing is a skill employers care about. Ask questions rather than issue commands: "Could this be zero?" beats "Wrong."
  • Fork vs collaborator: today you're collaborators, so you push branches here. To contribute to a project you don't have access to, you fork it, work in your copy, and open a PR back.
Hands-on · Lab 3 · 12 min

Fix a real bug

  1. Issues → label workshop-bug → pick an unassigned one → assign yourself
  2. Switch to main, pull. New branch fix/bug-NN
  3. Edit only the file named in the issue (one-line fix)
  4. Commit Fix bug NN: … → Publish Branch
  5. Open PR, description: Closes #<issue number>
  6. Check red → Details, read, fix, push again. Green → request review
  7. Review a classmate's PR

Full steps in LABS.md · Optional local test: python scripts/run_bug_test.py bug-NN

  • [48:00–60:00] NN is the two-digit bug number: bug 7 → fix/bug-07. The branch name must match or the check fails.
  • Python 01–17, JavaScript 18–34, C++ 35–50. You don't need to know the language; read the summary and hint, the bug is one line.
  • The check runs the bug's tests. Red with a test message = fix not right yet. Red with a "files" message = you edited something else.
  • Pushing again updates the same PR; never open a second one.
  • Local test needs that language installed; the GitHub check works regardless.
  • Instructor merges green PRs.
Part 8

Git for real projects

Senior design, research, internships

  • [60:00] Let people finish Lab 3 quietly while you talk. 10 minutes for this section.

Organize the repo

my-robot/
├── README.md        what, why, how to run
├── .gitignore       what Git should skip
├── docs/            reports, diagrams
├── src/             code, firmware
├── hardware/        schematics (small exports)
└── tests/
  • [~1.5 min] Folder names matter less than consistency. Agree as a team on day one.
  • Look at this workshop repo as an example: docs/, exercises/, scripts/, a README at the top.

READMEs: your project's front door

# My Robot
Line-following robot for ECE 4xx.

## Setup
1. Install **Python 3**
2. Run `python main.py`

- [Report](docs/report.pdf)
  • # headings
  • **bold**, `code`
  • 1. / - lists
  • [text](link)
  • What it is · how to run · who · status
  • [~2 min] Markdown = plain text with light symbols; GitHub renders it nicely. The README is the first thing a recruiter sees.
  • This repo's README.md is written to be a model: open it after the workshop.

What not to commit

Keep out

  • Build output (build/, *.exe)
  • Huge CAD files, datasets, videos
  • Secrets: passwords, API keys

Instead

  • List them in .gitignore
  • Big binaries: Git LFS or shared drive
  • Secrets: a local file that's ignored
  • [~2 min] .gitignore: one pattern per line, e.g. build/, *.log, .env. GitHub offers templates when you create a repo.
  • A pushed secret is public forever (bots scan GitHub within minutes). Rotate it, don't just delete the file.
  • Git LFS (Large File Storage) exists for big binary files; ask before using it on a team.

Habits that save teams

  • Pull before you start
  • One branch per task
  • Small commits, often
  • Good messages: Fix motor stall at low PWM, not stuff
  • PR + review before main
  • [~1.5 min] Good message: imperative mood, says what and why, under ~50 characters for the first line.
  • Senior design: protect main, use issues for tasks, review each other's PRs, write the README in week one, not the night before the demo.
